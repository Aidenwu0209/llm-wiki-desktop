# Product Parity Matrix: nashsu/llm_wiki and Obsidian Shell

This document captures current shell parity before any UI changes. It is meant to split later product work into focused PRs, not to solve those gaps here.

Baseline checked:

- Current repo: `Aidenwu0209/llm-wiki-desktop` at `01e36e6` (`main`, 2026-05-28).
- Reference app: `nashsu/llm_wiki` at `ff84ee9` (`Release 0.4.14`, 2026-05-26).
- Obsidian baseline: standard desktop vault shell behavior: file explorer, backlinks, graph, markdown reading/editing, command palette, settings, and plugin ecosystem.

Status labels:

- `same`: current shell has the same product surface and the same user path.
- `better`: current shell gives stronger behavior for the LLM Wiki product goal.
- `worse`: current shell has a missing or weaker shell capability.
- `intentionally different`: current shell diverges by product boundary, usually to keep local-first, runtime-owned, or proposal-first behavior.

## PR Decomposition Guidance

Use this order so each PR has one product question and one verification surface:

1. `shell(file-tree)`: add a recursive read-only vault tree.
2. `shell(markdown-reader)`: move markdown reading into the main workspace with outline/tabs.
3. `shell(backlinks)`: add a backlinks/source refs pane from existing metadata.
4. `shell(graph-engine)`: decide evidence graph vs vault graph and improve only that surface.
5. `shell(search-index)`: add local full-text search before optional vector search.
6. `settings(section-parity)`: make reserved settings honest and implemented.
7. `ingest(import-parity)`: split source watch, web clipper, and broader file support into separate PRs.
8. `writeback(review-ux)`: improve proposal review/apply UX without bypassing approval.

Security and boundary notes for follow-up PRs:

- Do not store real API keys in settings, vault state, tests, fixtures, docs, or examples.
- Keep local paths as the default. Hosted LLM, cloud OCR, web search, vector embedding, and external API paths must remain disabled until the user explicitly configures them.
- Do not add direct source/concept writeback in a shell parity PR. It needs an explicit product decision and its own review.
